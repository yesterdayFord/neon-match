## Workloads

The baseline uses the current deterministic benchmark workloads from `src/bench.zig`:

- `matching`: alternates one resting sell with one crossing buy; live orders stay at 0 or 1.
- `resting`: cycles 128 non-crossing buys followed by cancels for those same ids.
- `cancel_heavy`: repeats submit, cancel existing, cancel missing, cancel missing.
- `full_capacity`: prefills the bid side to capacity, then submits non-crossing buys expected to reject.

These cover the current simple engine's representative paths: matching, resting insertion/removal, cancellation misses, and capacity rejection.

## Journal Throughput

Command pattern:

```sh
zig build bench -Doptimize=ReleaseFast -- --measurement throughput --mode journal --workload matching --commands 1000000 --warmup 10000 --journal-dir .zig-cache/bench-baseline-journal-<rep>
```

| Workload | Throughput min | Throughput median | Throughput max | Final live orders | Checksum |
| --- | ---: | ---: | ---: | ---: | ---: |
| `matching` | 203181 | 255014 | 261531 | 0 | 500000 |

Journal mode measures record serialization, checksum work, and buffered writes accepted by the OS page cache. It does not measure stable-storage durability because NeonMatch does not issue per-command `fsync` or `fdatasync`.

## Allocation Verification

Matcher mode is the measured hot path for allocation behavior. Inspection found no allocator use in `src/engine.zig` or the benchmark warmup/measurement command loops for matcher mode. The engine uses fixed `OrderBook` arrays, stack-local command state, and no allocator-bearing API while applying benchmark commands.

The only allocator use in `src/bench.zig` is CLI argument parsing before warmup and measurement. Journal mode opens directories/files and writes records by design, so it is recorded as persistence overhead rather than the allocation-free matcher hot path.
